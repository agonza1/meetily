# Native call detection on macOS

Enable **Detect possible calls** in Recordings settings or the menu-bar panel. This is a new permission, not a migration of the Google Meet preference. While it is enabled the Chrome extension detector is inactive. Enable **Start after visible countdown** separately for hands-free recording. The countdown runs in Meetily's focused main window; changing focus resets it. Cancel or stop to suppress this activity session. Native detection never stops a recording; use Stop to save normally.

The detector polls public Core Audio process properties without opening a device, creating a tap or reading samples. It requires four seconds of concurrent running input and output for one application family. Related helpers must share both an outer application bundle path and an ancestor. Unattributable processes are skipped. A family is eligible again after eight seconds without either stream. If process metadata is unavailable, use manual recording.

Krisp can process input and output with no call in progress. Its outer app bundle (`ai.krisp.krispMac`), including nested helpers, is excluded from both detection and the final pre-capture check. This does not exclude a calling app that uses a Krisp device: that app's own streams are still eligible.

Stream activity is a heuristic, not a call or speech identifier: multiple tabs of one browser can combine unrelated input and playback; a muted call may keep a stream running or release it. Silence is not a hang-up. No native app, browser call, mute behavior or saved live transcript is certified by the synthetic tests.

## Isolated Apple Silicon acceptance (required before merge)

On an arm64 Mac running 27.2.1, a metadata-only snapshot of the running Chrome family returned **one active HAL process with input=1 and output=1**. Its call state was unknown; this is attribution evidence, not a positive call test. No window, tab or audio content was inspected. To repeat a snapshot during each controlled step, compile `frontend/src-tauri/src/audio/process_activity.c` with `clang -DMEETILY_ACTIVITY_PROBE -framework CoreAudio -framework CoreFoundation` and run the resulting executable with the test browser's main PID as its only argument.

Confirm the owner has no active recording and only one Meetily will run. Use a private test profile, a ready local model, headphones and synthetic speech only. Compare both settings surfaces and confirm legacy Meet opt-in leaves native detection off. With [pc1](https://webrtc.github.io/samples/src/content/peerconnection/pc1/) or the [audio-only alternative](https://webrtc.github.io/samples/src/content/peerconnection/audio/), record the actual Chrome HAL process directions at Start, Call, Hang Up and tab close. Start alone and unrelated playback must not trigger. Check detect-only prompt, cancel without retry, then a fresh call and a visible countdown to exactly one recording. Check live text, elapsed time, pause/resume, normal stop and saved nonempty transcript. Keep audio and transcript private. Record app/OS versions, flags and outcomes, including when tracks remain open; do not substitute a synthetic snapshot for this gate.
